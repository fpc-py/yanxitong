## 竞赛获奖级方案 · 全链路工程优化 · 可解释安全架构

竞赛核心策略：**用一个真实科研场景的端到端演示证明系统价值**，所有工程优化围绕“让这个演示在任何评委环境下都能稳定跑通”来设计。

### 差异化竞争力矩阵

| 维度    | 市面同类工具     | 研析通2.0           | 竞赛加分逻辑       |
| ----- | ---------- | ---------------- | ------------ |
| 知识准确性 | 纯向量RAG，易幻觉 | GraphRAG双引擎+引用溯源 | 每个结论可追溯到原文   |
| 数据处理  | 给出代码片段     | 代码沙箱+自动Debug闭环   | 评委现场可验证      |
| 科研闭环  | 单点工具       | 找→读→算→写全链路       | 演示完整性        |
| 工程成熟度 | Demo级      | 可观测性+CI门禁+成本控制   | 评委看到“能上线的东西” |
| 可解释性  | 黑盒输出       | 决策链可视化+证据图谱      | 科研场景刚需---    |

> **一句话定位**：以课题组文献库与实验记录为知识底座，构建 "KG×RAG 双引擎 + 分层多智能体协作 + 全链路可观测" 的 AI 科研合伙人，覆盖 "文献调研 → 知识构建 → 数据挖掘 → 实验设计 → 论文合规" 五大环节，让科研经验可复用、可追溯、可审计。

           │          │          │          │
    ┌──────▼──┐ ┌─────▼───┐ ┌───▼────┐ ┌──▼──────────┐

### 1.3 五类 Agent 详细设计

#### Agent 1: 🕵️ Retriever & Parser Agent（文献侦察与解析员）

| 维度       | 设计                                                                                          |
| -------- | ------------------------------------------------------------------------------------------- |
| **模型**   | DeepSeek-V3（长上下文 + 高性价比，128K 上下文窗口）                                                         |
| **工具**   | Arxiv API、Semantic Scholar API、CNKI 模拟适配器、Grobid PDF 解析服务                                   |
| **输入**   | 研究方向关键词 + 时间范围 + 期望文献数量                                                                     |
| **输出**   | `List[PaperSummary]`（结构化：研究问题、方法、数据集、实验结果、局限性、引用链）                                          |
| **容错**   | Arxiv 不可用 → 降级仅用 Semantic Scholar；PDF 解析失败 → 回退 PyPDF2 纯文本提取 + 标记 `parse_quality: degraded` |
| **幻觉控制** | 每个提取字段绑定原文 `span_range`（起止位置），无法定位的字段标记 `UNVERIFIED`                                        |

```
Retriever 内部子状态机：
  search → fetch_metadata → download_pdf → parse_structure
     │           │                │               │
     └── 超时 30s ─┘── 重试 3 次 ─┘── 文件 >50MB 拒绝 ─┘── 解析失败 → 降级
```

#### Agent 2: 🧠 Knowledge Graph Builder Agent（领域知识构建者）

| 维度       | 设计                                                                     |
| -------- | ---------------------------------------------------------------------- |
| **模型**   | qwen-plus（实体识别 + 关系抽取，成本可控）                                            |
| **工具**   | Neo4j 5.26、BGE-M3 嵌入服务、FAISS 索引                                        |
| **输入**   | Retriever 产出的 `List[PaperSummary]`                                     |
| **输出**   | 增量知识图谱 + 研究空白分析报告 + 技术演进路线图                                            |
| **关键优化** | 批量 MERGE（一次 Cypher 事务最多 500 条）；节点去重采用 `(title_hash + arxiv_id)` 联合主键   |
| **幻觉控制** | 关系抽取采用 Few-shot + Schema 约束（仅允许预定义 8 种关系类型）；抽取后做反向验证（抽取的关系能否在原文找到支撑句？） |

```
KG 构建流水线：
  PaperSummary[] → NER + RE（批量）→ Cypher MERGE → 一致性校验
                                                    │
                                          ┌─────────▼─────────┐
                                          │ 反向验证（幻觉检测） │
                                          │ 抽样 20% 关系人工复核 │
                                          └───────────────────┘
```

#### Agent 3: 📊 Data Analyst Agent（数据挖掘与实验员）

| 维度     | 设计                                                                             |
| ------ | ------------------------------------------------------------------------------ |
| **模型** | qwen-coder（代码生成专项） + qwen-plus（结果解释）                                           |
| **工具** | Docker 安全沙箱（替代 E2B，自托管可控）、Python 3.11 + Pandas/Scikit-learn/Matplotlib/Seaborn |
| **输入** | 用户上传数据集（CSV/Excel/JSON）+ 分析意图                                                  |
| **输出** | 清洗后数据 + 统计图表 + 分析报告 + 可复现代码                                                    |
| **容错** | **自动 Debug 闭环**：代码执行 → 报错 → LLM 分析错误 → 修复 → 重执行（最多 3 轮）                        |

```
沙箱安全策略：
  - CPU 限制：2 核
  - 内存限制：4GB
  - 执行超时：120s
  - 网络隔离：仅允许访问白名单 PyPI 镜像
  - 文件系统：只读挂载数据集，写入仅限 /tmp/output
  - 禁止的系统调用：os.system, subprocess with shell=True, eval, exec
```

#### Agent 4: 🧪 Experiment Designer Agent（实验方案优化师）

| 维度       | 设计                                           |
| -------- | -------------------------------------------- |
| **模型**   | qwen-max（深度推理，需要高质量建议）                       |
| **工具**   | KG 查询接口、Optuna 超参数优化引擎、SOTA 方法库              |
| **输入**   | 用户当前实验配置 + KG 中的相关方法                         |
| **输出**   | 优化建议 + 对比分析表 + 推荐配置代码                        |
| **幻觉控制** | 每条建议必须引用 KG 中具体 Paper 节点（含 Arxiv ID），无引用不出建议 |

#### Agent 5: 📝 Academic Reviewer Agent（学术规范审查官）

| 维度     | 设计                                           |
| ------ | -------------------------------------------- |
| **模型** | qwen-plus（规范检查，规则明确，不需要高推理）                  |
| **工具** | Zotero API、BibTeX 生成器、LaTeX/Word 模板引擎、查重模拟接口 |
| **输入** | 用户论文草稿（LaTeX/.docx）                          |
| **输出** | 逐段审查报告：引用格式问题、学术表达建议、潜在学术不端标记                |
| **安全** | **绝不直接修改用户论文**，仅输出建议列表 + 原文位置映射              |

## 2. 深度工程优化

### 2.1 Token 成本控制（五层策略）

```
┌─────────────────────────────────────────────────────────────┐
│  Layer 1: 智能模型路由 (Model Router)                        │
│  ┌──────────────┬──────────────────┬──────────────────┐     │
│  │ 任务复杂度     │ 模型选择           │ 预估成本/1K tok  │     │
│  ├──────────────┼──────────────────┼──────────────────┤     │
│  │ 意图识别/分类  │ qwen-turbo        │ ¥0.0003          │     │
│  │ 实体抽取/摘要  │ qwen-plus         │ ¥0.002           │     │
│  │ 代码生成       │ qwen-coder        │ ¥0.002           │     │
│  │ 深度推理/方案  │ qwen-max          │ ¥0.02            │     │
│  │ 长文献解析     │ deepseek-v3       │ ¥0.001/M tok     │     │
│  └──────────────┴──────────────────┴──────────────────┘     │
├─────────────────────────────────────────────────────────────┤
│  Layer 2: 语义缓存 (Semantic Cache)                          │
│  - 嵌入向量相似度 >0.95 的查询 → 直接返回缓存结果               │
│  - Redis 存储：key = MD5(embedding), value = 响应 + TTL 24h   │
│  - 预期命中率：文献查询 40%，概念问答 30%                       │
├─────────────────────────────────────────────────────────────┤
│  Layer 3: Prompt 压缩 (Prompt Compression)                    │
│  - 长上下文使用 LLMLingua-2 压缩至原始长度 40%                  │
│  - 保留关键实体、数字、引用，去除非必要修饰语                    │
│  - 对 Retriever 文献全文输入尤其有效                           │
├─────────────────────────────────────────────────────────────┤
│  Layer 4: 批处理 (Batch Processing)                           │
│  - 文献解析：攒够 10 篇后批量调用 DeepSeek（降低 API 调用次数）  │
│  - KG 导入：单次 Cypher 事务合并最多 500 条节点/关系            │
├─────────────────────────────────────────────────────────────┤
│  Layer 5: Token 预算管控                                      │
│  - 每用户/会话 Token 配额：50K tokens                           │
│  - 超出后切换至 qwen-turbo 或提示用户                          │
│  - Grafana 实时仪表盘展示消耗趋势                              │
└─────────────────────────────────────────────────────────────┘
```

**预期成本**：单用户完整科研流程（文献调研 + 数据分析 + 论文审查）控制在 ¥0.5-1.5，远低于人工助研成本。

### 2.2 幻觉解决全链路（六道防线）

```
用户提问
   │
   ▼
┌─────────────────────────────────────────────────────────┐
│ 防线 1: 检索增强 (RAG) — 从源头限定知识边界                │
│ → 所有回答基于检索到的文献片段 + KG 邻居节点                │
│ → 检索不到相关内容 → "未找到相关文献"而非编造              │
├─────────────────────────────────────────────────────────┤
│ 防线 2: 引用锚定 (Citation Anchoring)                      │
│ → 每个事实性陈述绑定 (paper_id, section, paragraph_idx)    │
│ → Agent 输出格式：{claim, evidence_span, source_paper}     │
├─────────────────────────────────────────────────────────┤
│ 防线 3: KG 事实校验 (Knowledge Graph Fact-Check)           │
│ → 抽取 Agent 输出中的 (方法, 数据集, 指标) 三元组           │
│ → 在 KG 中反向查找验证 → 不一致标记 Hallucination_Flag     │
├─────────────────────────────────────────────────────────┤
│ 防线 4: 自一致性采样 (Self-Consistency)                    │
│ → 同一问题 LLM 生成 3 个独立回答（temperature=0.7）         │
│ → 投票/语义聚类 → 不一致的回答降低置信度                    │
├─────────────────────────────────────────────────────────┤
│ 防线 5: 置信度校准 (Confidence Calibration)                │
│ → 每个 Agent 输出附带 0-1 置信度分数                        │
│ → <0.6 → 标记 "Low Confidence" → 触发人工复核              │
│ → 基于历史准确率动态调整（类似 ECE 校准）                   │
├─────────────────────────────────────────────────────────┤
│ 防线 6: 人工熔断 (Human Circuit Breaker)                   │
│ → 连续 3 次低置信度输出 → 暂停 Agent 回答                  │
│ → 推送人工审核请求 → 审核通过后恢复                         │
└─────────────────────────────────────────────────────────┘
```

### 2.3 工具防翻车机制

| 问题场景           | 解决方案                                                     |
| -------------- | -------------------------------------------------------- |
| **API 超时/不可用** | 熔断器模式：连续 3 次失败 → 熔断 60s → 半开探测 → 恢复或继续熔断                 |
| **PDF 解析异常**   | 多级降级：Grobid → PyPDF2 → OCR Tesseract → 标记 `parse_failed` |
| **沙箱代码死循环**    | Docker `--ulimit cpu=120` + 看门狗进程 120s 强杀                |
| **KG 写入冲突**    | Neo4j MERGE 幂等 + 写锁超时 10s → 重试 3 次                       |
| **向量检索返回空**    | 回退关键词 BM25 检索（Elasticsearch 内置）                          |
| **LLM 输出格式不符** | JSON Schema 约束 + Pydantic 校验 → 不合法则重试（最多 2 次）+ 记录异常      |

## 3. 可解释性与安全性

### 3.1 全链路可解释性设计

- **推理轨迹面板**：展示Orchestrator的路由决策→各Agent的思考过程→工具调用参数与结果

- **证据链面板**：每条输出结论→对应的证据ID→原始文献段落/图谱路径

- **成本面板**：每次交互的token消耗、各Agent分摊、缓存命中情况

```
用户界面展示层次（从表层到深层）：

Layer 1 — 最终回答（带引用标记[1][2]...）
    │
Layer 2 — 推理步骤可视化（类似 CoT，展示 Agent 思考链路）
    │  "步骤1: 检索到 12 篇相关文献 → 步骤2: 提取 5 个关键方法
    │   → 步骤3: 在 KG 中验证 → 步骤4: 综合回答"
    │
Layer 3 — 溯源面板（点击任何引用可查看）
    │  源论文标题、段落原文、在 PDF 中的位置
    │
Layer 4 — 审计日志（面向开发/评估）
    │  完整 State 快照、每次 LLM 调用、每个工具调用、
    │  Token 消耗、置信度变化、Agent 路由决策
```

**实现方式**：

- LangGraph 的 `checkpointer` 自动保存每个 Node 的输入/输出
- 前端 `AuditPanel` 组件从 checkpointer 读取并渲染
- 所有 Agent 输出统一包装 `TraceableOutput{content, citations, confidence, reasoning_steps}`

### 3.2 安全性设计

| 安全层面       | 具体措施                                           |
| ---------- | ---------------------------------------------- |
| **输入安全**   | 用户输入经 LLM Guard 过滤（防止 prompt injection、越狱提示）   |
| **代码执行安全** | Docker 沙箱：网络隔离 + 资源限制 + 禁止系统调用白名单              |
| **数据安全**   | 用户数据按 `tenant_id` 隔离；敏感实验数据本地处理（不发送云端 API）     |
| **学术诚信**   | 查重检测集成；禁止直接生成完整论文（仅辅助建议）；所有 AI 参与标记            |
| **访问控制**   | JWT + RBAC（学生/导师/管理员三级权限）；API 限流每用户 30 req/min |
| **内容安全**   | 输出经阿里云内容安全 API 审核（涉政/涉黄/涉暴）                    |

## 4. 系统评估方案

### 4.1 四层评估体系

```
                    ┌──────────────────────┐
                    │  L4: 业务效果评估      │  ← 用户满意度、科研效率提升
                    │  (Human Evaluation)   │
                    ├──────────────────────┤
                    │  L3: 任务完成质量      │  ← 各 Agent 端到端准确率
                    │  (Task-Level Metrics) │
                    ├──────────────────────┤
                    │  L2: 组件性能评估      │  ← 检索 Recall、KG 准确率、代码执行成功率
                    │  (Component Metrics)  │
                    ├──────────────────────┤
                    │  L1: 基础能力评估      │  ← RAGAS、幻觉率、一致性
                    │  (Foundation Metrics) │
                    └──────────────────────┘
```

### 4.2 各层具体指标

#### L1: 基础能力评估

| 指标                           | 方法                       | 目标值   |
| ---------------------------- | ------------------------ | ----- |
| **幻觉率 (Hallucination Rate)** | 金标集人工标注 200 条 QA，检查事实性错误 | <5%   |
| **答案一致性 (Self-Consistency)** | 3 次采样语义相似度均值             | >0.85 |
| **上下文忠实度 (Faithfulness)**    | RAGAS 指标：回答中可归因于上下文的占比   | >0.90 |
| **答案相关性 (Answer Relevance)** | RAGAS 指标                 | >0.85 |

#### L2: 组件性能评估

| 组件           | 指标               | 方法                  | 目标               |
| ------------ | ---------------- | ------------------- | ---------------- |
| Retriever    | Recall@10, MRR   | 30 个标准查询 + 人工标注相关文献 | Recall@10 > 0.85 |
| KG Builder   | 实体识别 F1, 关系抽取 F1 | 人工标注 500 篇论文的实体和关系  | F1 > 0.80        |
| Data Analyst | 代码执行成功率          | 50 个标准数据分析任务        | >90%（含自动修复后）     |
| Reviewer     | 引用格式检测准确率        | 50 篇含人工植入错误的论文      | >95%             |

#### L3: 任务完成质量

| 任务   | 指标            | 评估方式          |
| ---- | ------------- | ------------- |
| 文献调研 | 覆盖度（是否遗漏关键论文） | 领域专家对比标准文献列表  |
| 实验优化 | 建议采纳率         | 用户反馈 + 实验效果对比 |
| 论文审查 | 问题检出率 vs 人工审查 | 双盲对比          |

#### L4: 业务效果

- **用户满意度 NPS**：目标 >40
- **任务完成率**：用户发起的科研任务成功完成比例 >85%
- **时间节省**：文献调研时间从平均 3 天缩短到 30 分钟

### 4.3 CI/CD 评估门禁

```yaml
# .github/workflows/eval-gate.yml
评估流水线:
  金标集测试:
    - 幻觉率检测: 阈值 <5%

  组件测试:

```

### 4.4 持续评估与 A/B 测试

- **影子模式部署**：新版本 Agent 先以影子模式运行（只记录不展示），对比生产版本
- **A/B 测试框架**：10% 流量路由至实验组，对比核心指标
- **数据飞轮**：用户纠错反馈 → 自动生成微调样本 → 定期 LoRA 更新

### 竞赛评估的消融实验设计
